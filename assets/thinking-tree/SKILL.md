# 树形思考链（thinking-tree）

把当前任务的思考过程写成**一棵可读、可改、可执行的树**，并保存在工作区里，让人和模型看同一份东西。

用户可以在右侧边栏把这张图当思维导图看（滚轮缩放、拖拽平移），并直接修改；你在实现任务前必须先读它，并按照里面的要求去做。

## 执行纪律

这棵树不是展示，是**契约**：

- 你的每一份工作都要能追溯到第二层的某条**要求**。动手前说清楚在做哪条，做完把结果写回那条节点。
- 树里写的技术路线、工具、风格、验收标准是硬约束，不是建议。
- 用户改过的内容优先于你的判断。有冲突就写明理由并把选择权交回去，**不许悄悄改回去**。
- 没有证据就不许宣布完成。证据 = 文件内容、命令输出、接口的实际返回、页面的实际行为。

## 自检（selfcheck）

`00-goal.md` 的 front matter 里有一个开关：

- `selfcheck: on` —— 每轮结束会自动开始下一轮（宿主在 turn/end 后唤醒你，最多 40 轮）；
- `selfcheck: passed` —— 已通过，不要自检；
- 空 —— 关闭。

面板右上角的「自检」按钮就是它的开关。开启后你会收到一条 `【思考链自检 第 N 轮】`，照这个做：

1. 读 `thinking-tree/` 全部节点。
2. 逐条核对第二层的**要求**是否真的达成，且**有证据**（文件、命令、接口、页面行为）。拿不出证据就算未完成。
3. 未完成 → 该节点 `status: blocked`，正文写清缺什么，然后**立刻继续做**，别停下来解释。
4. 全部达成且有证据 → `00-goal.md` 的 `selfcheck` 改成 `passed`、`status` 改成 `done`，正文补一节「结果：…」。
5. 通过之前**不要动 `selfcheck`**，也不要宣布完成。

## 什么时候用

- 任何**多步骤**任务开始时（下载、搭建、重构、写文档、做插件、排查问题…）。
- 任务中途技术路线变化时（换方案、加约束、砍掉一条路）。
- 用户说"先想清楚""列个方案""画一下思路""thinking tree""思考链"时。
- 用户已经在右侧边栏改过这棵树时——此时**必须先重读**再动手。

单步小事（改个错别字、回答一个问题）不要建树。

## 目录契约

- 位置：**当前工作区根目录**下的 `thinking-tree/` 文件夹。
- 一个块 = 一个 `.md` 文件，全部平铺在这一个文件夹里（**不要建子目录**）。
- 以 `_` 开头的文件是给人看的说明（如 `_index.md`），渲染时会被跳过，你可以写。
- 文件夹不存在就创建它。

## 每个节点可以指定模型

front matter 里的 `model: provider/model`（例如 `deepseek/deepseek-chat`）。空 = 跟随当前会话模型。
右侧面板抽屉里的「模型」下拉就是改这条字段，节点右上角会标出模型。

动手实现某条节点前**先看它的 `model`**：

- 空 → 你自己做。
- 有值 → 用 `subagent` 把这条节点的具体工作派出去，`provider` / `model` 用这个值，prompt 里放节点标题和正文要点；子代理返回后，把结果写回该节点正文，状态置 `done`。
- 派活时把节点正文当简报，不要复制整棵树。

节点上的 `model` 只写 `provider/model`，不写解释、不写"因为…所以用…"。

## 文字怎么写

**只交代工作，不写废话。** 节点上的每个字都要有信息量：

- 标题：一句动宾短语。"点右侧按钮弹出侧边栏"、"轮询变化签名"。不要"关于…的思考"、"深入分析"这种壳。
- 正文：写做了什么、用了什么、结果是什么。命令、路径、接口名、数字优先。
- 不写：比喻、口号、自我评价（"完美解决"、"效果很好"）、复述目标、给目标写序言、结尾总结陈词。
- 一条一句。能一行说完就不要三行。
- 状态已经是"完成"的节点，正文只留结果和验证方式，不要留过程感想。

```
好：\`ctx.sidebarRightTabs.register({ id, kind })\` + \`slots.register\` 到 sidebar.right.pane.tab
坏：这里我们巧妙地复用了内置的右侧栏能力，从而优雅地避免了重复造轮子的复杂度
```

## 整体型项目的第二层模板

有些任务不是"实现一个功能"，而是"做出一件完整的东西"——代码动画、音乐制作、前端设计这类，必须先把整体拆成设计维度，否则做到一半才发现风格不对、时长不够、排版崩了。

这类任务的第二层**直接用下面的维度**（按项目删减，不要漏），第三层写**怎么实现 + 要查什么资料**，第四层写具体动作。

### 代码动画 / 动效短片

| 第二层维度 | 要定什么 |
|---|---|
| 风格设计 | 参考片、色调、材质、字体、颗粒/噪点 |
| 镜头设计 | 景别、机位、推拉摇移、转场方式 |
| 动效设计 | 缓动曲线、节奏、入出场、循环方式 |
| 细节设计 | 次级动效、粒子/光晕、残影、遮罩 |
| 画面元素设计 | 主体、背景、装饰、图标、贴图 |
| 时长设计 | 总时长、段落节拍、帧率、循环点 |
| 文字内容设计 | 标题/字幕/文案、字数上限、字号层级 |
| 画面排版设计 | 网格、安全区、对齐、留白 |

第三层写法示例：`Canvas + requestAnimationFrame` / `GSAP` / `Remotion` / `Three.js`，并写清「要查的：GSAP 时间轴 API、某个参考片的配色、字体授权」。

### 音乐制作

| 第二层维度 | 要定什么 |
|---|---|
| 风格设计 | 流派、参考曲、情绪、年代感 |
| 结构设计 | 段落（intro/verse/chorus/bridge/outro）、小节数、调式、BPM |
| 音色设计 | 乐器、合成器预设、采样来源 |
| 编曲层次 | 声部、频率分配、副歌加什么 |
| 律动设计 | 节奏型、swing、groove、留白 |
| 混音设计 | 电平、EQ、压缩、声场宽度、人声处理 |
| 时长设计 | 总长、各段秒数、能否循环 |
| 交付设计 | 响度目标（LUFS）、格式、母带处理 |

第三层写「用什么工具 + 参考什么」：DAW、具体插件、采样库、参考曲的分析点。

### 前端设计

| 第二层维度 | 要定什么 |
|---|---|
| 风格设计 | 视觉语言、色彩体系、字体、圆角/阴影尺度 |
| 信息架构 | 页面、路由、核心数据与状态 |
| 布局栅格 | 断点、栅格列数、间距尺度、容器宽 |
| 组件设计 | 原子组件清单、状态（默认/悬停/禁用/加载/错误） |
| 交互与动效 | 过渡时长曲线、反馈、骨架屏 |
| 响应式与可访问性 | 断点行为、对比度、键盘可达、语义标签 |
| 内容与文案 | 文案层级、语气、空状态与错误提示 |
| 性能与交付 | 技术栈、构建产物、首屏指标、部署方式 |

第三层写「用什么实现 + 查什么规范」：设计系统、无障碍标准、框架文档、性能预算。

## 五层结构

树的**深度**决定它属于哪一层，不需要额外标注。**目标第一层，要求第二层，后面三层依次是方案、技术路线、具体步骤。**

| 深度 | level | 回答的问题 | 数量 |
|---|---|---|---|
| 0 | `goal` | 用户要实现的**目标**是什么——一句话，可验收 | 1 个 |
| 1 | `requirement` | 用户**明明白白提出的要求**：一条一个节点，尽量保留原话 | 2–8 个 |
| 2 | `plan` | 这条要求**大致怎么做**：分几步、涉及哪些部分、要不要外部资源 | 每条要求 1–3 个 |
| 3 | `route` | 具体用**什么技术实现**：语言/库/框架/接口/数据结构/风格 | 每个方案 1–3 个 |
| 4+ | `step` | 具体到**做什么、怎么做**：命令、文件、参数、顺序 | 按需 |

要点：

- **第二层只放"用户要的"，不放"我打算做的"**。用户说"点右边按钮弹出侧边栏"是一条要求；"复用内置右侧栏"是方案；"注册 sidebarRightTabs + 槽位"是技术路线；"调 openTab" 是步骤。
- 一路往下都应该更具体，不能上层比下层还细。
- 一条要求可以只到方案层就停（还没想好技术路线）——不要为了对称硬凑。
- 底层的 step 要能直接被验证完成：跑通了一条命令、写出了某个文件、某个接口返回了对的东西。

## 文件格式

```markdown
---
id: 01-req-panel
parent: 00-goal
order: 1
title: 点右侧按钮从侧边弹出侧边栏
status: pending
updated: 2026-01-01T00:00:00.000Z
---

# 点右侧按钮从侧边弹出侧边栏

正文用 Markdown 写清楚就行。
```

字段：

- `id` — 本文件内的稳定标识，默认等于文件名去掉 `.md`。**建好后不要改**，别人用 `parent` 指向它。
- `parent` — 父节点的 `id`。根节点写 `""`（空）或 `parent: null`。
- `order` — 同级排序，从 0 开始，升序。
- `title` — 卡片标题，一句话。
- `status` — `pending` | `active` | `done` | `blocked`。同一时刻只让一条处于 `active`。
- `updated` — ISO 时间戳，改动时更新。

文件名约定：`NN-slug.md`，`NN` 与 `order` 一致。父子关系**只由 `parent` 决定**，文件名只是给人看的：

```
thinking-tree/
├── 00-goal.md
├── 01-req-panel.md
├── 02-req-mindmap.md
├── 02-1-svg-layout.md
├── 02-2-wheel-zoom.md
└── 03-req-live.md
```

## 工作流

### 1. 开始时：先读，再写

1. 列出 `thinking-tree/*.md`（`glob` 或 `ls`）。
2. 有就**全部读一遍**——用户可能已经改过内容、加过约束、删过步骤。
3. 没有就建：先写 `00-goal.md`（目标），再把它拆成 2–6 条**要求**节点，最后给每条要求写它的技术路线和步骤。
4. 用户明确要求"先给方案"时，**先停在这棵树里**，写完就汇报，不要直接开始实现。

### 2. 过程中：实时更新

每完成或改变一个真正的步骤，就落盘一次：

- 开始做某条 step → `status: active`
- 做完了 → `status: done`，并在正文补一行"结果：…"（命令、文件路径、验证方式）
- 走不通 → `status: blocked`，正文写清**卡在哪、缺什么、需要用户做什么决定**
- 路线变了 → 改对应节点的正文，或新建一条并给旧的标 `blocked`

**不要攒到最后一次性写**。用户是靠这张图在看你在想什么。

### 3. 实现时：树是契约，不是草稿

动手前用 `read` 读一遍相关的节点文件，然后：

- 树里写的路线、工具、风格、验收标准，就是你要实现的东西。
- 用户手动改过的内容**优先级高于你的记忆**。即使你觉得原来的方案更好，也按用户改的做。
- 如果用户的修改有事实问题或做不通：**不要偷偷改回去**。在一个新节点或该节点正文的"注意"里说明冲突和理由，把选择权交回用户。
- 树里没写但你判断必须做的，先补一个节点再动手，这样这件事是可见的。

### 4. 结束时

- 所有 step 收成 `done`，或明确标 `blocked` 并写原因。
- 在 `00-goal.md` 正文末尾补一小节"结果"，写清交付了什么、怎么验证。
- 不要把树删掉——它是这次任务的思考存档。

## 用户会怎么改

右侧边栏的思维导图里（点窗口右边缘的按钮，或侧边栏的思考链卡片）：

- 滚轮缩放、拖拽空白处平移；**左键长按某个块可以把它挪开**（坐标会写进该节点 front matter 的 `x`/`y`，顶栏「自动排列」清掉）；
- 点任意节点在下方抽屉里**直接编辑它的 Markdown** 并保存；
- 节点左侧的小圆点切换状态；
- 可以加子节点、删除节点（连同它的子树）。

这些都是直接改上面的 `.md` 文件。所以你读到的永远是最新的；**不要缓存树的内容跨轮次使用**。

## 别这么干

- ❌ 把整棵树写进一个文件里（一节一个大标题）——必须是**一块一个文件**。
- ❌ 建子文件夹分类。
- ❌ 改已有节点的 `id` 或文件名（会让 `parent` 指向空气）。
- ❌ 整份重写节点文件时把 front matter 丢掉。`id` / `parent` / `order` / `x` / `y` / `model` / `selfcheck` 一个都不能少——丢了节点就脱离父节点、坐标失效、自检开关消失。要么用面板改，要么 `write` 时把原 front matter 原样带上。
- ❌ 把"我打算怎么做"塞进第二层（第二层是用户的要求）。
- ❌ 只写目标不写要求，或只写路线不写具体命令。
- ❌ 用户改过之后，按自己记忆里的旧方案继续做。
