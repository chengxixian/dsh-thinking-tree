# 自检一轮

面板上点了「自检」之后，你收到的这句就是自检的启动信号。不要只回复文字，要真的动手核对。

## 回复格式（必须遵守）

第一行固定写成：

```
> 🧪 正在自检 · 第 N 轮
```

N 取自 `00-goal.md` 的 `selfcheck-round`（没有就写 1）。

结束时最后一行二选一：

```
> ✅ 自检通过
```

```
> ⛔ 自检未通过 · <一句话说清缺什么>
```

其它内容按平常写，但这两行必须有——对话气泡上要能看出「正在自检」和结果。

## 先判断该不该现在自检

看 `thinking-tree/` 里当前这棵树的节点状态：

- 还有 `active` 或 `pending` 的节点，说明**活儿没干完**：先继续把活干完（该做的做、该改的改），这一轮不要宣布结果。
- 只有全部 `done` / `blocked`，才进入下面的核对。
- 用户刚提了新要求而树上还没有对应节点：先补节点，再自检。

换句话说：自检不是「现在立刻判分」，而是「把没做完的先做完，然后拿着证据判分」。用户如果在项目刚开始就点了自检，也是这个规则——先把项目做完。

## 核对办法

1. 读 `00-goal.md` 和全部节点，重点是**第二层的每一条要求**。
2. 逐条找证据，只认这三种：
   - 文件/产物存在，而且内容确实是要求的东西（打开看，不靠印象）；
   - 命令真的跑通，有输出；
   - 页面/接口的真实行为（截图、返回体、日志）。
3. 没有证据 = 未完成。**不许**因为"应该没问题"就判通过。
4. 未完成的：把该节点 `status` 改成 `blocked`，正文写清缺什么、卡在哪，然后立刻继续做。
5. 全部达成且有证据：把 `00-goal.md` 的 `selfcheck` 改成 `passed`、`status` 改成 `done`，正文补一段「结果：…（证据清单）」。
6. 还没达成：`selfcheck` 保持 `on`，不要改。

## 别这么干

- 只回一段"我检查过了，没问题"而不写证据。
- 把没做的事标成 `done`。
- 为了让自检通过而删掉要求节点。
- 在活儿没干完时就写 `✅ 自检通过`。
