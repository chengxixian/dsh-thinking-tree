# 需求拆解

收到任何要求，动手之前先拆。拆得细不细，直接决定后面做得对不对——拆错一步，后面全在错的方向上返工。

**这条规则不靠"想起来"**：系统提示里每轮都带着它，所以每轮都必须执行。这个技能是详细手册，规则本身不用激活。

## 五个问题，缺一不可

对每条要求，先在心里（然后落到文件里）回答这五个：

1. **要什么**——一句话，去掉所有形容词，只留动词和名词。
2. **做成什么样**——验收标准。必须能测：哪个文件存在且内容是什么、哪条命令跑通、页面/接口表现出什么行为。写不出可测标准，说明还没拆明白。
3. **拆成几块**——互不重叠的子任务，每块对应一个交付物。块与块之间不共享"半个"产出。
4. **每块怎么做**——步骤、工具、技术路线。写清"用 X 做 Y，因为 Z"。
5. **每块怎么验证**——证据形态：跑哪条命令、看哪个文件的哪一行、点哪里看到什么。

## 粒度：拆到"能独立验证"为止

- 一个节点 = 一个交付物 = 一次可验证的完成。
- 一个动作应该能在 5–30 分钟内做完；写不出这么小的动作，说明还在"想法"层。
- 一个节点里出现"并且/然后/同时"这类连接词，多半该拆成两个节点。
- 反过来，拆到"打开文件""保存文件"这种就过度了——那是操作，不是交付物。

## 节点正文的固定写法

每个要求节点（第二层）的正文必须包含这四段，缺一段就是没拆完：

```
## 做成什么样
<可验收的形态：文件/接口/页面/输出>

## 怎么做
1. <步骤 + 工具 + 技术路线>
2. ...

## 怎么验证
- <命令 / 路径 / 操作，以及预期的结果>

## 要查什么资料
- <文档、参考、规范；没有就写"无">
```

方案节点（第三层）写技术路线；动作节点（第四层）写具体做什么。**不要**把"怎么做"塞进要求节点里就完事——要求节点写"做成什么样"，方案节点写"怎么做"。

## 拆之前先排歧义

- 要求里有歧义（"好看""流畅""专业"）：先给一个可验收的解释，写进节点，再动手；别猜着做。
- 要求之间冲突：在树里并列两个节点，正文写清冲突点，按用户可能最在意的先做。
- 要求太大（"做个平台"）：先切成能独立交付的第一块，做完再切下一块；不要一次铺 40 个节点。

## 拆完自检（动手前最后一眼）

- [ ] 每条要求都能回答"做成什么样"，且这个标准能被别人验证。
- [ ] 每条要求至少有 1 个方案节点，方案节点下至少有 1 个动作节点。
- [ ] 没有任何节点写的是"优化一下""完善一下""处理一下"。
- [ ] 没有任何节点塞了两件不相关的事。
- [ ] 每条要求都写了"怎么验证"。

任一条不满足 → 回去补，别开始做。

## 例：把"做个宣传视频"拆开

❌ 不合格：`做宣传视频` / `优化画面` / `完善音效`

✅ 合格：

- 要求：`1 分钟竖屏宣传片，含 3 个卖点`
  - 做成什么样：`out/promo.mp4`，1080×1920，时长 60±2s，音量 -14 LUFS
  - 怎么验证：`ffprobe out/promo.mp4` 输出分辨率/时长；抽 3 帧确认卖点字幕
- 方案：`REMOTION 渲染 + 手写字幕` → 动作：`搭 composition，跑通 5 秒样片`
- 方案：`素材与配乐` → 动作：`选 2 首候选，导出 60s 裁剪版`

子块再细也遵守同一套：做什么、做成什么样、怎么验证。
